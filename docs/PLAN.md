# QRCode 基础设计与实施计划

初始规划日期：2026-09-22。2026-09-23 已按用户补充完成实现并部署，实际验收记录见 QA.md。

最新范围覆盖原始计划：首版完全不处理桌号，餐厅点击直接跳转；菜单仅保留类型接口约定，不实现获取。首页标题为“下一餐，吃什么？”，副标题为“是啊，吃什么？”。竖屏优先紧凑餐厅列表，减少列表之前的内容。

目标地址：https://qrcode.royilab.com；管理员入口：/admin。

2026-09-23 用户修订（覆盖下文原版发布与密码流程）：餐厅仅名称必填，链接与地点均可暂时留空；发布不依赖地点设置，不强制试打开或勾选。可选信息收起，上传自动识别后直接发布。密码最少 6 位，接受纯数字和重复字符；线上管理员密码按用户指定重置，完成初始化后不再强制修改。无链接餐厅显示“点餐入口待补充”。

## 1. 产品目标与第一版范围

用户真正需要的是“找到这家餐厅，然后立即进入正确的点餐页面”。二维码是管理员导入入口的数据来源；访客的主操作是点击点餐。

- 访客无需注册或登录。管理员使用独立密码会话。
- 按用户最后的要求，第一版只允许管理员上传；不提供访客上传接口。
- 首页固定展示管理员指定地点的餐厅。“附近”指该地点附近，不暗示已读取访客位置。
- 地点可设置名称、完整地址、说明；坐标为选填。无定位授权弹窗，不显示未经计算的距离。
- 管理员管理餐厅名称、分店、地址/楼层、分类、排序、点餐入口及发布状态。
- 管理员上传二维码照片，浏览器自动解码出网址，经过预览和试打开后发布。
- 访客点击“开始点餐”，在当前浏览器进入商家网页；返回本站时恢复搜索与滚动位置。
- 不代替商家系统处理菜单、购物车、订单或支付。商家是否要求登录由商家系统决定。
- 第一版不做用户投稿、多地点发现、地图搜索、实时营业状态或自动链接巡检。

目前尚缺首个地点的名称/地址和真实餐厅二维码。开发可使用明确标注的测试数据，正式公开目录不能把测试数据当作真实餐厅。

## 2. 访客界面

视觉方向：温暖、清晰的街区餐厅目录。米白底色、深色文字、单一暖橙强调色；大店名、简短地址、稳定对齐。避免用大型宣传区占用手机首屏。

首页从上到下：

1. QRCode 品牌与当前地点，显示“此地点附近的点餐入口”。
2. 餐厅搜索框；有足够内容时展示简洁分类筛选。
3. 餐厅卡片：店名、分店/地址、必要的使用说明和“开始点餐”按钮。
4. 次级入口“查看二维码”，打开大图与复制链接；不要求同一部手机再次扫码。
5. 空列表、无搜索结果、加载失败均提供清晰说明；加载失败可重试。

通用网页入口一次点击进入；首版不收录桌号入口、不设置桌号确认弹窗。未验证入口保持草稿。

### 响应式规则

| 场景                  | 设计规则                                                     |
| --------------------- | ------------------------------------------------------------ |
| 窄手机、折叠屏外屏    | 单列，320 CSS px 起无横向溢出；主要按钮高度至少 48 px        |
| 大手机、分屏窗口      | 按实际容器宽度排版，不根据设备名称判断                       |
| 折叠屏展开、平板      | 卡片达到舒适宽度才增加到两列；宽屏最多三列，限制内容总宽     |
| 双屏/有遮挡区域的设备 | 支持时读取屏幕分段信息避开铰链；缺乏支持时保持普通响应式布局 |
| 管理员手机端          | 分步表单；上传、预览、发布可以全程单手完成                   |
| 管理员平板端          | 表单与预览并排，桌面表格在窄屏转为卡片                       |

正文默认至少 16 px，长店名换行；支持键盘操作、清晰焦点、减少动画偏好和安全区域。折叠/展开、旋转和软键盘弹出不重置表单。文字对比度按 WCAG AA 检查。

## 3. 管理员流程与识别策略

流程：登录 → 设置地点 → 新增餐厅 → 上传照片 → 自动识别 → 核对网址与用途 → 试打开 → 发布。

- 输入支持手机拍照和相册选择，首版接受 JPEG、PNG、WebP；建议限制单文件 10 MB、解码像素 24 MP。浏览器不支持的 HEIC 提示转为截图或 JPEG。
- 解码在管理员浏览器执行；识别模块仅在上传页按需加载，并放进 Web Worker 避免卡住界面。
- 原生 BarcodeDetector 仅作为可用时的加速路径，必须有跨浏览器解码器回退；选型在实施时用真实样本验证，不依赖原生 API 覆盖所有设备。
- 优先从原始像素识别，再生成用于保存的清晰规范化图片，避免先过度压缩导致识别失败。
- 多二维码图片要求管理员裁剪或明确选择，不能静默采用第一个结果。
- 解码失败可裁剪、旋转或重新上传；手动填写网址作为明确标注的备用方式，仍需相同验证。
- 保存完整原始 URL，包括查询参数和 fragment，不随意清理参数，以免破坏商家签名或桌号信息。
- 发布前显示目标主机名与链接，管理员明确验证商家、门店和入口用途；“试打开”不执行下单或支付。
- 仅允许 HTTP/HTTPS 网页作为直达入口，优先 HTTPS；HTTP 需显式提示。拒绝脚本、data、file、带用户密码的网址及本地/内网字面地址。
- 小程序码、应用专用协议、支付码、纯文本码不能标记为“浏览器直接点餐”。照片可保留为草稿，需补充可用网页入口后发布。
- 首版只保存通用网页点餐入口；不增加桌号字段或桌台逻辑。无法确认是通用网址或存在会话专属参数的链接保持草稿。
- 状态为草稿、已发布、已停用；替换链接先形成草稿，验证发布后替换旧版本。

## 4. 技术架构与数据

建议使用 TypeScript + React/Vite 前端，单个 Cloudflare Worker 承载同源 API 与静态资源；D1 保存结构化数据，私有 R2 保存规范化二维码图片。无需独立虚拟服务器或额外认证供应商。

```text
访客浏览器 ── 获取地点/已发布餐厅 ── Worker ── D1
     │                                │
     └─ 点击点餐 ── 商家网页           └─ 受控图片读取 ── R2

管理员浏览器 ── 密码会话 ── Worker
     └─ 本地图片解码、预览 ── 鉴权上传 ── R2 + D1 草稿
                                  └─ 管理员试用核对 ── 发布
```

数据模型控制在必要范围：

| 数据       | 核心字段                                              |
| ---------- | ----------------------------------------------------- |
| 地点       | 名称、地址、说明、可选坐标；首版单个活动地点          |
| 餐厅       | 所属地点、店名/分店、地址、分类、排序、状态           |
| 点餐入口   | 餐厅、URL、图片对象键、状态、验证时间；首版与餐厅共表 |
| 管理员配置 | 密码加盐哈希、强制改密标记、会话版本                  |
| 会话       | 随机令牌的哈希、有效期、撤销状态                      |

主要接口：公开读取地点与已发布餐厅、读取已发布图片；管理员登录/退出/改密、地点设置、餐厅与入口的增改/发布/停用、图片上传。所有写入在服务端验证权限，不依赖前端隐藏按钮。

图片先作为草稿对象写入，再完成数据库关联；失败时清理新对象。替换成功后清理旧对象，避免上传失败损坏现有入口。

初期公开动态列表使用重新验证策略，管理员接口与会话响应禁止公共缓存；图片使用内容版本键。管理后台发布成功后，访客刷新即可看到新数据。API 返回错误不能被 SPA fallback 伪装成成功的 HTML。

## 5. 管理员安全与凭据

- 按需求保留初始密码 000000。推荐只在受保护的初始化阶段有效，首次进入必须改密；新密码设置前不能发布或改写目录。
- 初始化入口不能先带默认密码裸露到公网等待认领；在本地连接远端初始化或临时保护环境完成设置后，再开放正式后台。
- 密码校验在服务端进行；存储带随机盐的密码哈希，部署前验证所选算法与参数在 Workers 中可用并满足合理成本。
- 会话 Cookie 使用 HttpOnly、Secure 和 SameSite；建议 8 小时有效。退出与改密立即撤销旧会话。
- 登录失败限流与递增等待；写接口验证 Origin/CSRF 防护，阻止跨站表单代操作。
- 限制上传字节数、图片尺寸与允许格式；服务端检查文件签名，拒绝 SVG/HTML 等主动内容，随机生成对象键。
- 服务端再次验证 URL 与字段，数据库使用参数化查询，页面按纯文本显示店名等用户内容。
- 首版不由服务器主动抓取点餐 URL，避免产生 SSRF 与自动访问商家带来的副作用。URL 格式校验不能证明商家身份，人工试开仍是必要发布步骤。
- 私有 R2 中的草稿照片只允许管理员读取；公开图片接口只返回已发布入口关联图片。
- Cloudflare/GitHub 凭据只用于部署和版本管理，不发给前端，不写入仓库或日志。运行时秘密使用 Cloudflare Secrets；CI 使用仓库 Secrets。
- 本次消息中已经出现凭据，建议在实际部署前撤销并换成最小权限凭据，通过本地环境或凭据存储配置。本计划不保存或复述这些值。

## 6. 设计与工程审计

这是方案层面的自审，尚无代码、真实二维码或线上站点可供验证。下列处置已纳入计划，不代表已通过运行测试。

| 级别 | 发现                                      | 计划处置与验证                                     |
| ---- | ----------------------------------------- | -------------------------------------------------- |
| 高   | 二维码可识别不等于可以浏览器点餐          | 实际入口试开；应用码/支付码/失效码保持草稿         |
| 高   | 桌码可能绑定他人桌台或会话                | 首版不收录；管理员发布前确认是无需桌号的通用入口   |
| 高   | /admin 只是地址，默认密码不能提供有效保护 | 服务端鉴权、限流、受保护初始化、首次改密、会话撤销 |
| 高   | 只在前端控制上传权限容易绕过              | 直接请求每个写 API 和上传 API，验证未登录时拒绝    |
| 中   | 原生识别 API 覆盖不足                     | 回退解码器；Safari/Chrome 与真实手机样本测试       |
| 中   | 模糊、多码、超大图片影响识别与内存        | 尺寸限制、裁剪、后台线程、明确错误与重试           |
| 中   | 发布与图片上传部分失败造成坏数据          | 草稿状态、关联提交与失败清理；注入失败测试         |
| 中   | 缓存或 SPA 路由导致旧数据、伪成功         | 明确缓存与 API 路由；发布后刷新、下线后访问测试    |
| 中   | 折叠和旋转时输入丢失或按钮跨铰链          | 容器布局与状态保留；模拟视口测试加可获得的真机验证 |
| 中   | 域名、账户权限、R2 可用性未确认           | 部署阶段先做只读检查，再创建专用资源               |

结论：方案可以进入原型和实现；正式发布依赖真实入口验证、管理员初始化和部署权限检查。未发现必须增加大型服务的需求。

## 7. 执行顺序与验收

| 阶段             | 交付                                      | 验收条件                                   |
| ---------------- | ----------------------------------------- | ------------------------------------------ |
| 1. 可点击原型    | 首页、二维码预览、管理员上传与地点设置    | 访客容易找到点餐；手机/展开屏/平板排版清晰 |
| 2. 核心功能      | D1/R2、密码会话、二维码解码、草稿与发布   | 管理员上传到访客点击的完整流程跑通         |
| 3. 审计与测试    | 权限、异常、识别、响应式与可访问性报告    | 高优先级问题关闭；未验证项明确列出         |
| 4. GitHub 与部署 | 专用仓库、构建检查、Cloudflare 资源和域名 | HTTPS 可用，真实数据可查，版本可追踪和回滚 |

核心验收矩阵：

- 访客：无登录浏览、搜索、进入正确门店页面、返回恢复状态、空状态和网络失败重试。
- 管理员：初次改密、错误密码限流、退出、会话过期、撤销会话、匿名写入/跨站写入被拒绝。
- 解码：清晰码、旋转码、反光/低清码、多码、无二维码、非网页码、非图片、大图与不支持格式。
- 数据：创建、编辑、重复提交、发布、停用、替换、上传失败、数据库失败、草稿不公开。
- 设备：320/360/390/430/768/820/1024/1280 CSS px；横竖屏、200% 字号/缩放、软键盘与安全区域。
- 浏览器：Safari、Chrome；微信内置浏览器作为补充场景。真实折叠屏如未获得，不把模拟结果称为真机验收。
- 性能：公共首页不下载二维码解码库，不一次加载全部二维码大图；移动网络下及时显示目录。性能目标在原型阶段建立基线。

部署步骤：

1. 验证 Cloudflare 账户、royilab.com 的活动 zone、目标子域名现有记录、Workers/D1/R2 权限和服务是否启用。涉及现有域名冲突先报告，不覆盖无关服务。
2. 使用专用项目与资源命名；GitHub 默认新建专用私有仓库，仓库归属在部署时确认；不改变其他项目 remote。
3. 仓库包含源码、数据库迁移、测试、部署说明和 lockfile；忽略本地 secrets、原图和环境文件。
4. 建立 GitHub 检查流程；部署凭据仅存放于适当的 secrets 位置。未确认所需计费服务前不承诺永久免费。
5. 完成受保护的管理员初始化，部署 Worker + 静态资源并绑定 qrcode.royilab.com。
6. 填入真实地点与已核对二维码，检查 DNS、TLS、/admin、直接刷新路由及公开/后台权限。
7. 记录发布版本；回滚代码前检查数据库兼容性，迁移优先采用可向后兼容的新增操作。破坏性迁移前备份数据。

## 8. 已核对的官方依据

- [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/)：支持一次部署静态资源与 Worker，适合该同源小应用。
- [D1](https://developers.cloudflare.com/d1/) 与 [R2](https://developers.cloudflare.com/r2/)：分别承载结构化数据和图片对象。
- [Workers Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)：需要活动 zone；域名绑定涉及现有 DNS 记录检查。
- [Workers Secrets](https://developers.cloudflare.com/workers/configuration/secrets/) 与 [Workers Best Practices](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/)：用于部署及鉴权实现审查。
- [Barcode Detection API](https://developer.mozilla.org/en-US/docs/Web/API/Barcode_Detection_API)：原生接口存在兼容性限制，因此计划包含跨浏览器回退。

应用技能：Cloudflare、Frontend Design、Workers Best Practices；PowerShell Safe Invocation 用于本地文件操作。本次未执行独立代理审计，审计结果为本轮方案自审。
