# QRCode 实施与验收记录

验收日期：2026-09-23（Asia/Singapore）。本轮为实现者自审和自动化验证，没有独立代理审计。

## 多语言与抽签增量验收

管理员为餐厅填写繁体、英文名称及位置和介绍，浏览器发布后公开 API 保留这些字段。简体、繁体、英文切换时正确显示对应内容，旧餐厅缺少译文时仍显示原始内容。语言选择在本机浏览器保留，分类和界面文案随之切换。

「今天吃什么」默认纳入全部已发布餐厅，按分类缩小到单个餐厅后抽取结果正确；清空选择时抽签按钮不可用；只手动勾选一家后也正确抽到该餐厅。普通模式有翻动/光环动画，系统要求减少动态效果时直接给出结果。320 × 568、360 × 740、390 × 844、768 × 1024、820 × 1180、1024 × 768 均无横向溢出，320 × 568 首屏餐厅区域仍占 51%。

## 2026-09-23 发布流程修复

根因：新增和更新餐厅时，服务端强制要求另一页的全局地点名称及地址。餐厅内的地址无法满足这一条件，因此反复填写也会被拦截。已移除全局地点前置条件，地点地址也改为选填；餐厅只有名称必填，链接留空时不生成点餐跳转。

取消强制试打开及确认勾选；名称前置，二维码和链接集中显示，其他资料折叠，底部保留草稿和发布按钮。密码规则改为最少 6 位并允许纯数字及重复字符。

本轮通过：5 个单元测试、TypeScript 与生产构建；`scripts/check-publishing.mjs` 验证地址留空的新增/编辑/发布、URL 完整保留、空名称与危险网址拒绝、改成 `000000` 并直接登录。Chromium 实际上传二维码自动解码后直接发布、只填名称发布均成功；390 × 844 与 820 × 1180 已检查编辑界面。

以下为原版验收记录，其中“强制核对才能发布”和“必须改用更长密码”的流程已被以上用户修订替代。

## 已实现范围

## 已发现并处理的问题

- 初版手机首屏前置区域过高：根据用户反馈删除重复地点说明与英文引导，缩短标题区、压缩餐厅卡片。
- 图片尺寸需要同时限制总像素与单边尺寸：后端现限制 24 MP 且单边不超过 8192。
- 仅靠公开默认密码存在被先行初始化的风险：首次登录同时要求随机初始化链接，改密后直接用 `/admin`。
- 部署中打开的旧后台引用旧资源：本地连续构建时出现一次旧 chunk 加载失败；刷新到当前版本后完整上传流程通过。管理员发布新版本后应刷新旧页面。
- 默认 DNS 读取权限不足：已通过账户级 Workers 自定义域名接口成功绑定域名，后续 Wrangler 部署也已成功更新该绑定。
- 线上域名自动注入 Cloudflare Web Analytics 脚本，与严格 CSP 冲突：已仅放行 Cloudflare 的指标脚本与采集域名，保留其余来源限制。

## 实际限制

- 没有真实商家二维码可验证其点餐业务。自动识别和网页跳转已验证，商家菜单、登录与付款由商家网站负责。
- 没有在真实折叠屏、Safari、微信内置浏览器上验收；目前是 Chromium 尺寸模拟及桌面浏览器测试。兼容性回退解码器已打包，不以原生 BarcodeDetector 为唯一依赖。
- 首版不内置图片裁剪工具；管理员遇到多码或模糊图片需先裁剪/重拍，也可手动粘贴已核对网址。
- 尚未进行正式流量负载测试；数据库、图片上传、登录均有输入界限，未实现大型多地点目录能力。
